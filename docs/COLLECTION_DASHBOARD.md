# 本地示范采集 Dashboard

## e2 专项防护（2026-11-16）

面板新增启用后的 e2 监测：异常回退隔离数、非法 e2 拒绝数和待复核数，并可下载 `e2-events.jsonl`。这些数字不追溯部署前的棋谱；历史数据使用 `audit-e2` 单独审计，避免混淆旧断点与新回复。

已识别的异常回退会重连并有限重试，旧 Polling 或升级路径上的可疑 e2 会自动改用 WebSocket 首连。持续异常时显示 `suspect_e2` 暂停信息，保留原历史，不计弃局、不启动替代棋局。正常开局和前进 e2 保留；其他距离/往返信号先检查连接并记录复核标记，不等同于判坏棋。请求日志中的 `requested_transport`、实际 `transport`、`recovery_transport` 和 `recovery` 区分原配置与自动恢复路径。详见 [e2 排查记录](BARRICADE_E2_INVESTIGATION_20261116.md)。

同一请求通道或全批连续 6 次非法 e2 会触发 `e2_service_unhealthy` 并保存断点暂停，避免继续批量弃局。恢复请求仍保持原设备身份、难度和完整棋谱；明确限流/拒绝不走自动换路。

质量策略 v2 还会隔离造成完整盘面第三次重复的 e2，再换新连接求解。完整盘面包括双方棋子、墙、余墙和行动方；墙变化后的绕路不算循环。第二次重复只标记复核。API 的 `e2_health.quality_version` 表示当前策略版本，逐步诊断和事件保留各自版本。

质量策略 v3 对距离疑点 e2 增加原局面新会话复核，面板区分“原局面复核换步”“两次一致”和仍未独立复核的已接受距离疑点。替换候选和确认事件不重复计入未复核样本；旧版已经接受的疑点仍保留在历史计数中。正式棋谱只保存最终的新鲜远端应手，第一次候选及两次请求证据保存在诊断中。

## 并发和请求限制

16 条连接、共享 0.10 秒间隔的配置方法和 Master 对 Expert 实测记录见 [采集提速指南](COLLECTION_SPEED_TUNING.md)。

Dashboard 每批最多可填 **10,000 盘**，其中最多 **100 盘**同时保持进行中，并且同时运行盘数不能超过本批总盘数。默认同时运行 1 盘。「每条连接的盘数」留空时所有棋局共用一条连接。同批 6 盘、每连接 3 盘时，两个独立队列各轮转 3 盘，可各有 1 个应手请求在途。设为每连接 1 盘时，每个活动棋局使用自己的连接。所有连接共用同一个设备标识与全局请求间隔。间隔默认 1 秒，可设为 0.05 秒或更长。收到明确限流时暂停采集并保留检查点。

| 同时运行盘数 | 每连接盘数 | 连接数 | 全局请求间隔 | 理论发起上限 |
| ---: | ---: | ---: | ---: | ---: |
| 6 | 3 | 2 | 1 秒 | 60 次／分钟 |
| 4 | 1 | 4 | 0.35 秒 | 约 171 次／分钟 |
| 5 | 1 | 5 | 0.30 秒 | 200 次／分钟 |

100 盘和 0.05 秒是本地配置边界。Barricade 的服务端配额没有确认。6 条连接共用 0.05 秒时曾收到明确的 `rate_limited`。所有连接合计按配置的间隔发起请求，增加连接可以减少等待回复造成的空档。发出速度接近间隔上限时，继续增加连接无法提高这个上限。

Master 对 Master 实测中，四条连接共用 0.35 秒时，回复正常的窗口约为 165 条有效应手／分钟。五条连接共用 0.30 秒时，无错误的短测约为 187–196 条／分钟，另一个包含非法回复和重试的约 47 分钟窗口实测约为 118 条／分钟。每分钟有效应手只统计合法且已落盘的走法。非法应手和明确限流分别记录。

| 共享间隔 | 测量时长 | 合法步／分钟 | 排除开局第一步后的合法步／分钟 | 非法回复比例 | 新增自然完局 |
| --- | --- | --- | --- | --- | --- |
| 0.30 秒 | 300 秒 | 21.60 | 12.80 | 87.70% | 0 |
| 1.00 秒 | 222.891 秒 | 8.61 | 5.92 | 85.52% | 0 |

此次降频未提高有效吞吐，已恢复共享 0.30 秒。它是非随机短窗口对照，基线包含暂停、重连影响，不能据此推断服务端限流机制或保证未来速度；前述回复正常时的速度也不代表当前性能。重开产生的开局第一步应单独统计，避免把不断开新局误认为完整棋谱产量增加。精确时间窗、应手计数和对照结果保存在该批目录的 `rate-diagnostics/pace-quality-baseline-20261115.json`、`pace-quality-1s-20261115.jsonl` 和 `pace-quality-comparison-20261115.json`。

## 正式采集队列

下面的 PowerShell 命令在本地 Dashboard 已启动且没有待续跑的正式队列时，建立 15 种搭配、25 个批次，共 75,000 盘。需要从空历史开始时，先暂停并归档旧目录，或启动 Dashboard 时用 `--output` 指定新的采集目录。

```powershell
$settings = @{
    games_per_matchup = 5000
    connections = 4
    request_interval = 0.35
    illegal_move_retries = 2
} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8770/api/campaigns' `
    -ContentType 'application/json' -Body $settings
```

先跑 Master 对 Master，优先处理包含高档 AI 的搭配。同档对局收集 5,000 盘自然完局。不同档的搭配各执红方收集 2,500 盘自然完局，合计 5,000 盘。正式队列使用标准开局、关闭缓存、不设整批时间上限。每条连接一次推进一盘。

正式队列强制使用 `completed_only: true`：目标和恢复时的剩余盘数只统计 `status="completed"` 的自然完局。达到动作上限的截断棋谱照常保存在 `episodes.jsonl`，放弃棋局另存，但这两类都不占自然完局目标，采集器会补开棋局。普通单批默认仍以保存棋谱数（自然完局加截断）为目标，也可在创建或恢复时勾选「仅自然完局计入目标」。Dashboard 的进度条和目标卡使用实际目标计数；「已保存棋谱」仍包含截断，可能大于自然完局目标。详情 API 的 `target_games_saved` 表示计入目标的盘数，`games_saved` 保留已保存棋谱总数的原含义。

单盘重试后仍收到非法应手时，采集器记录拒绝原因并保留棋局断点。其它棋局继续推进，搁置的棋局稍后补跑。当前正式队列的调速实测保存在首批目录的 `rate-diagnostics/connection-tuning.jsonl`，采集进度和导出文件可在 Dashboard 查看。

发生可重试的连接故障时，正式队列会重新请求同一局面一次，并写入 `transport-retries.jsonl`。重试仍失败或收到明确限流时，当前批次暂停，从 Dashboard 恢复可接着原来的棋局跑。

2026-11-16 起，新建连接默认直接使用 WebSocket 握手。`request_transport` 可设为 `websocket`（WebSocket 首连）、`polling` 或 `upgrade`（先 Polling 再升级），恢复 API 也接受此字段。`proxy_env` 明确控制是否使用现有环境代理，默认 false，对 HTTP 和 WebSocket 一致生效。批次状态栏显示已保存的选择。连接失败不会自动切回 Polling，因为绕过代理的 Polling 初始化路径已反复出现错误应手。已有批次可保留断点并以 `{"request_transport":"websocket","proxy_env":false}` 恢复，原难度、目标和历史不变。正式运行建议先采用保守共享请求间隔观察自然完局，不将传输修复当成提高并发的依据。

新鲜成功应手的 `metadata.request_diagnostics` 和失败诊断均包含实际发送前缀、行动方、手数、匿名 `connection_id`、连接内序号、`requested_transport`、实际 `transport` 与 `proxy_env`。其中 `requested_transport=upgrade` 即使实际 `transport=websocket`，仍属于 Polling 建立的会话。设备标识不写入这些请求字段。完整证据及验收见[此次排查记录](BARRICADE_E2_INVESTIGATION_20261116.md)。

### 优先补完积压棋局

新建正式队列默认开启「优先补完积压棋局」。已有批次先暂停，再在恢复表单中勾选该选项；普通单批也可以在创建或恢复时开启。对应 API 字段是 `drain_pending: true`，例如恢复请求正文 `{"concurrent_games":16,"request_interval":0.30,"drain_pending":true}`。未勾选的普通实验保留原调度方式。

开启后优先处理已有断点。未设置下述放弃阈值时，发生非法应手的棋局持续留在重试队列，积压补完后才开新局。相同局面连续失败时，冷却间隔按 30、60、120、240、300 秒延长，最高 300 秒；成功前进一步后重置。冷却期间连接可推进其他积压棋局。检查点保存当前历史和下一次可重试时间，暂停或重启后仍可恢复。明确限流和用户暂停仍会停止采集，不会在后台继续发出请求。

本地回归已复现旧调度的一种等待问题：测试中的 `retry-far` 已到重试时间，却要等 6 个初始待补棋局全部处理后才再次获得请求机会。公平调度修复已于 2026-11-15 19:18 加载到本地批次，68 项相关回归测试通过。它针对 `drain_pending: true` 的旧局选择，规则如下。

- 只选择已就绪棋局。检查点的 `retry_at` 尚未到达时，即使棋子接近终点也不会提前重试；没有就绪棋局时等待到期。
- 旧局选择交替使用「近终局优先槽」和「普通槽」。近终局候选满足 `min(State.distance(红方), State.distance(蓝方)) <= 2`，依次按双方最小距离、当前行动方距离选择；距离相同时优先已到期的重试，同一来源内保留原有顺序。这里的距离是考虑已放墙的 BFS 最短路径距离，只用于调度，不保证该局能在两步内获胜。
- 普通槽中，已到期的搁置重试局（`deferred`）和初始待补局（`initial pending`）都存在时交替选择来源；已到期重试局保持队列先进先出，初始待补局保持原来的按步数排序。这样普通棋局和已到期重试局都有继续推进的机会。

替换新局与旧局之间仍按原规则交替，本次修复不增加 Dashboard 控件，也不改变请求间隔、连接数、同一局面第 5 轮失败后的弃局规则或自然完局目标。实采验证需同时观察旧局等待时间、非首步合法应手和自然完局数，不能仅凭新开局数量或短窗口应手增多认定改善。

部署后的完整性检查确认 361 盘原积压的历史前缀、既有完局与弃局记录均保留，原示范数据字节前缀的 SHA256 一致。至 19:22:34，部署前的 3 盘近终局在新进程启动后 11.45、17.72、26.60 秒首次收到应手，其中两盘合法推进，尚无自然完局。这些时间包含启动和请求耗时，证明实际获得调度，尚不能证明总体吞吐或完局率提高。证据保存在本批次 `rate-diagnostics/priority-scheduling-verification.json` 与 `priority-dispatch-observation-20261115.json`。

Dashboard 会显示未完成棋局总数、待补跑数，以及每盘当前局面的连续失败轮数和冷却时间。「未完成棋局」包含等待中的断点，不等于同时在处理的连接数；在途峰值是上一段采集结束后写回的统计。逐步示范总数包含未完局棋局，应同时查看自然完局数来判断完整棋谱的产量。

这项策略解决本地积压的调度和续跑问题，远端非法 `e2` 的原因仍未修复，不能保证补跑速度或完成时间。采集始终验证每一步，只保存合法远端应手；不会跳过失败局面、用本地走法替代或补造动作。每盘既有的动作上限仍然有效，达到上限的截断棋谱单独统计。

### 超过失败阈值后放弃重开

在创建或恢复表单中勾选「连续失败超限时放弃重开」，填写允许失败轮数；默认输入为 4，表示**同一局面第 5 轮失败后放弃该盘**。这里计数的是失败轮数；设置两次即时重试时，一轮最多发送 3 次请求，不能把 4 轮理解成 4 个网络请求。成功走到新局面后计数重置。

API 字段为 `abandon_after_retries`。例如在暂停后恢复：`{"drain_pending":true,"abandon_after_retries":4}`。未填写该字段保留原配置；显式发送 `{"abandon_after_retries":null}` 关闭放弃规则。该设置不会改变连接数或全局请求间隔。

放弃棋局写入 `abandoned-games.jsonl` 和对应单盘 JSON，记录原历史、失败原因、失败轮数及阈值；此前取得的合法示范仍保留在 `transitions.jsonl`。放弃棋局不计入完成目标，采集器会启动新棋局补足名额；替换新局允许越过积压优先限制。Dashboard 单独显示「放弃棋局」数量、相关示范步数和可分页回放的列表，也可下载放弃棋谱 JSONL。示范总步数包含放弃棋局，完成进度不包含它们。
