# 提高 Barricade 棋谱采集速度

2026 年 11 月 15 日，Master 红方对 Expert 蓝方的本地采集采用逐档提速，最终使用 **16 条连接、每条连接推进 1 盘、所有连接共享 0.10 秒请求间隔**。标准开局、关闭缓存、单盘上限 256 步，整批时间上限留空。

这组配置复用现有 Dashboard、RemoteExpert 和 RequestGate。所有连接使用本机已有的同一个设备标识，RequestGate 统一安排请求发起时间。0.10 秒对应所有连接合计最多约 600 次请求／分钟；合法落盘速度还取决于响应耗时、非法应手和重试。

## 本次测量

每个档位运行期间，用新增的合法逐步示范数量除以测量秒数，再乘 60。每次切换先暂停原批次，再从相同批次的断点恢复。

本次最高档窗口约为起始窗口的 3.2 倍。四个窗口依次测量，涉及不同局面和不同时间的服务响应，因此这只是本次观测的吞吐变化。后续巡检出现过约 53～116 条合法应手／分钟的波动。服务端在这些测量窗口内没有返回明确限流，长期可用频率仍需持续观察。

## 在 Dashboard 调整已有批次

1. 打开本地 Dashboard 的运行与历史，确认批次的红蓝档位、标准开局和关闭缓存设置。
2. 查看原配置中的「每条连接的盘数」，应为 1。这决定 16 个同时运行的棋局对应 16 条连接。
3. 暂停当前批次，等待状态成为已暂停。
4. 在恢复设置中填写同时运行盘数 16、请求间隔 0.10 秒，然后恢复原批次。
5. 检查示范步数持续增加，并记录每分钟有效应手数、自然完局数、截断数、非法应手和连接错误。

每批实际连接数也受剩余盘数限制。Dashboard 的「非法应手待补跑」可以累积超过 16 盘；其中待补跑的断点不等于正在同时发送请求的连接数。「同时在途峰值」等汇总值由当前一段采集结束后写回，运行期间可能显示上一段的值。

## 通过本地 API 调整

在 macOS 或 Linux 终端执行以下命令。先用列表返回的 ID 填写 `RUN_ID`。

```bash
curl --noproxy '*' -fsS http://127.0.0.1:8770/api/runs
RUN_ID='填写已有批次ID'
curl --noproxy '*' -fsS \
  "http://127.0.0.1:8770/api/runs/$RUN_ID?limit=1"
```

确认该批次的 `config.games_per_connection` 为 1。处于 running 状态的批次先暂停。

```bash
curl --noproxy '*' -fsS -X POST \
  "http://127.0.0.1:8770/api/runs/$RUN_ID/pause"
```

重复查询详情，等待 status 为 paused 后执行恢复。已经暂停或失败的批次可以直接执行恢复命令。

```bash
curl --noproxy '*' -fsS \
  "http://127.0.0.1:8770/api/runs/$RUN_ID/resume" \
  -H 'Content-Type: application/json' \
  -d '{"concurrent_games":16,"request_interval":0.10}'
```

Windows PowerShell 的对应恢复命令如下。

```powershell
$runId = '填写已有批次ID'
$settings = @{
    concurrent_games = 16
    request_interval = 0.10
} | ConvertTo-Json
Invoke-RestMethod -Method Post `
    -Uri "http://127.0.0.1:8770/api/runs/$runId/resume" `
    -ContentType 'application/json' -Body $settings
```

`resume` 当前允许修改同时运行盘数和请求间隔。若已有批次使用其他每连接盘数，需先核对实际连接数再判断提速效果。

新建批次可以在 Dashboard 填写同样参数。API 创建参数示例如下，红蓝档位和目标盘数按本机负责的采集任务填写。

```json
{
  "red": "master",
  "blue": "expert",
  "games": 2500,
  "concurrent_games": 16,
  "games_per_connection": 1,
  "request_interval": 0.10,
  "illegal_move_retries": 2,
  "max_plies": 256,
  "time_limit_seconds": null,
  "opening": [],
  "use_cache": false
}
```

将上述 JSON POST 到 `/api/runs` 会立即启动单批采集。正式 campaign 的调度还支持非法应手暂缓、稍后补跑和一次瞬时连接错误重试，具体行为见 [Dashboard 指南](COLLECTION_DASHBOARD.md)。本次测试使用了这些 campaign 调度能力。默认 `/api/campaigns` 会建立全部难度搭配，使用前应核对任务范围。

## 持续运行与恢复

- 每 30～60 秒比较实际写入量，并观察至少数个窗口。提高连接数后如有效吞吐下降，可退回此前较好的档位。
- 收到 `rate_limited` 时保留断点并退避。优先遵循服务端给出的等待时间；没有等待时间时，本机巡检从 5 分钟开始退避。连续限流时延长全局间隔，必要时减少连接数。
- 非法应手由本地规则拒绝，记录错误并保留原局面。正式队列可以暂缓该盘，先推进其他棋局。
- 连接故障或临时文件锁恢复后继续原批次。出现暂停超时时，检查采集状态和文件最后写入时间。本次从 12 条连接升档时暂停超过 30 秒，随后重启原 Dashboard 并从原数据目录的检查点恢复。
- 使用额外的自动恢复程序时，同步更新它的连接数和间隔，避免恢复时覆盖手动设置。本机运行器和定时巡检已采用 16／0.10。
- `games` 是保存的棋谱总数，包含截断棋谱。目标若要求 2,500 盘自然完局，需按 `completed` 补足，截断棋谱单独保存和统计。

本次远端频繁返回非法 `e2`。增加并发提高了合法示范产出，但这种异常仍会发生。固定局面的额外对照中，立即重试成功 7/22 次、重连后重试 5/26 次、等待 3 秒再重试 4/22 次；重连与等待耗时更长，本机因此沿用原重试方式。恰好合法的 `e2` 无法仅凭响应判断是否来自同一异常，训练数据使用者需保留这个质量限制。
