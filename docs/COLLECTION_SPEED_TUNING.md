截至 2026 年 11 月 15 日 19:50，本机保留 **2 条连接、每条连接推进 1 盘、共享 1.0 秒间隔**。相邻五分钟对照中，合法应手由 46.4 增至 57.6 条／分钟，棋谱完整性检查通过，因此继续使用该配置观察；这不保证长期速度或不会限流。此前 **16 条连接、共享 0.10 秒**已收到明确 `rate_limited`，不能作为已验证的长期稳定配置。下方保留早期提速、单连接恢复和后续两连接实验的记录。

## 在 Dashboard 调整已有批次

1. 打开本地 Dashboard 的运行与历史，确认批次的红蓝档位、标准开局和关闭缓存设置。
2. 查看原配置中的「每条连接的盘数」，应为 1。这决定每个同时运行的棋局对应一条连接。
3. 暂停当前批次，等待状态成为已暂停。
4. 如需采用当前观察配置，在恢复设置中填写同时运行盘数 2、请求间隔 1.0 秒，然后恢复原批次。这是观察配置，不保证不会限流。
5. 检查示范步数持续增加，并记录每分钟有效应手数、自然完局数、截断数、非法应手和连接错误。

每批实际连接数也受剩余盘数限制。Dashboard 的「非法应手待补跑」可以累积超过同时运行盘数；其中待补跑的断点不等于正在同时发送请求的连接数。「同时在途峰值」等汇总值由当前一段采集结束后写回，运行期间可能显示上一段的值。

## 通过本地 API 调整

在 macOS 或 Linux 终端执行以下命令。先用列表返回的 ID 填写 `RUN_ID`。

```bash
curl --noproxy '*' -fsS http://127.0.0.1:8770/api/runs
RUN_ID='填写已有批次ID'
curl --noproxy '*' -fsS \
  "http://127.0.0.1:8770/api/runs/$RUN_ID?limit=1"
```

确认该批次的 `config.games_per_connection` 为 1。处于 running 状态的批次先暂停。

```bash
curl --noproxy '*' -fsS -X POST \
  "http://127.0.0.1:8770/api/runs/$RUN_ID/pause"
```

重复查询详情，等待 status 为 paused 后执行恢复。已经暂停或失败的批次可以直接执行恢复命令。

```bash
curl --noproxy '*' -fsS \
  "http://127.0.0.1:8770/api/runs/$RUN_ID/resume" \
  -H 'Content-Type: application/json' \
  -d '{"concurrent_games":2,"request_interval":1.0}'
```

Windows PowerShell 的对应恢复命令如下。

```powershell
$runId = '填写已有批次ID'
$settings = @{
    concurrent_games = 2
    request_interval = 1.0
} | ConvertTo-Json
Invoke-RestMethod -Method Post `
    -Uri "http://127.0.0.1:8770/api/runs/$runId/resume" `
    -ContentType 'application/json' -Body $settings
```

这里的 `resume` 仅调整同时运行盘数和请求间隔，保留既有的完成目标及失败处理配置。若已有批次使用其他每连接盘数，需先核对实际连接数再判断效果。

新建批次可以在 Dashboard 填写同样参数。API 创建参数示例如下，红蓝档位和目标盘数按本机负责的采集任务填写。

```json

  "red": "master",
  "blue": "expert",
  "games": 2500,
  "concurrent_games": 2,
  "games_per_connection": 1,
  "request_interval": 1.0,
  "illegal_move_retries": 2,
  "max_plies": 256,

  "opening": [],
  "use_cache": false,

  "abandon_after_retries": 4,

```

将上述 JSON POST 到 `/api/runs` 会立即启动单批采集。正式 campaign 的调度还支持非法应手暂缓、稍后补跑和一次瞬时连接错误重试，具体行为见 [Dashboard 指南](COLLECTION_DASHBOARD.md)。本次测试使用了这些 campaign 调度能力。默认 `/api/campaigns` 会建立全部难度搭配，使用前应核对任务范围。

## 持续运行与恢复

- 每 30～60 秒比较实际写入量，并观察至少数个窗口。提高连接数后如有效吞吐下降，可退回此前较好的档位。
- 收到 `rate_limited` 时保留断点并退避。优先遵循服务端给出的等待时间；没有等待时间时，本机巡检从 5 分钟开始退避。连续限流时延长全局间隔，必要时减少连接数。
- 非法应手由本地规则拒绝，记录错误并保留原局面。正式队列可以暂缓该盘，先推进其他棋局。当前 `abandon_after_retries: 4` 表示同一局面第 5 轮失败时放弃该盘；`illegal_move_retries: 2` 时，每轮最多请求 3 次，不是累计 5 个请求就放弃。成功推进一步后失败轮数重置。
- 连接故障或临时文件锁恢复后继续原批次。出现暂停或观察超时时，先核对原进程、API 状态和文件最后写入时间；超时本身不作为重启依据，避免重复启动采集器。
- 使用额外的自动恢复程序时，同步核对它的连接数和间隔，避免恢复时覆盖手动设置或误用旧的 16／0.10 参数。
- 正式 campaign 强制 `completed_only: true`，5,000 盘目标只统计自然完局；放弃和截断都单独保存，不占目标名额，自动补开新局的规则已经生效。普通单批未开启 `completed_only` 时仍以保存棋谱数（含截断）为目标；上述创建示例明确开启自然完局目标。

远端频繁返回非法 `e2` 的原因尚未确认。早期增加并发的短窗口提高过合法示范产出，但后续明确限流及低有效产量说明该结果不能外推。此前固定局面的额外对照中，立即重试成功 7/22 次、重连后重试 5/26 次、等待 3 秒再重试 4/22 次；这些小样本同样不能证明某种恢复方式长期有效。恰好合法的 `e2` 无法仅凭响应判断是否来自同一异常，训练数据使用者需保留这个质量限制。采集不跳步，不补造动作，也不以本地策略替代远端示范。
